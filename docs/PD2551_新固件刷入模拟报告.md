## 二、模拟发现的失配项（本次已全部修复）

### 1. 分区大小（不修 = fastbootd/OTA 刷入失败，非变砖）

| 参数 | 旧值 | 新值（OTA manifest 实测） |
|---|---|---|
| `BOARD_BOOTIMAGE_PARTITION_SIZE` | 134217728 | **100663296**（boot 实际 96MB） |
| `BOARD_SUPER_PARTITION_SIZE` | 9126805504 | **15571353600**（group main 15,567,159,296 + 4MB 元数据） |
| `BOARD_VIVO_DYNAMIC_PARTITIONS_SIZE` | 9122611200 | **15567159296** |
| 动态分区清单 | 含重复项 + cust/vgc | **system/system_ext/vendor/product/odm/odm_dlkm/vendor_dlkm/system_dlkm**（新 OTA group main 不含 cust/vgc，二者由 oem_zip 单独刷入） |

### 2. 内核 / 模块 / dtb / dtbo 全部换代

| 项 | 旧（16.0.15.3） | 新（16.0.17.1） |
|---|---|---|
| kernel | 6.6.89-android15-8（36MB） | **6.6.127-android15-8-g3b723d0e8507-abogki558077879**（17MB） |
| recovery 模块 vermagic | 6.6.89-android15-8-g131232aa79fe | **6.6.127-android15-8-gbd39053f6565**（124 个全部替换） |
| dtb | 451,808 B | **451,872 B**（内容变化） |
| dtbo | sha `7b15bd0f…` | sha `29593d13…`（内容变化） |

KMI 世代仍为 **android15-8**，未跨代。新固件原厂 recovery 片段含 303 个模块，树内 122 条 `modules.load.recovery` 清单在新固件中**零缺失**。

### 3. cmdline / 指纹版本串

- `product.version=PD2551_A_16.0.15.3.W10` → `PD2551_A_16.0.17.1.W10`（BoardConfig + package-vendor-boot.sh 兜底值）
- `BUILD_FINGERPRINT` incremental → `compiler261021233739`

### 4. 自检脚本误报修复

`check-vendor-fit.sh` 原来用宽匹配提取内核版本串，新 GKI 内核里第一个匹配是裸的 `6.6.127-`（无 KMI 段），导致模块 KMI 误报不一致。已改为只匹配 `x.y.z-androidN-M` 形式。

## 三、模拟实测过程与证据

1. **OTA 结构**：payload v2，manifest 39 个分区，全量 OTA（package-type=full），vivo 自定义 ZSTD_REPLACE 按 32MB 分块压缩——需按 manifest 的 dst_extents 逐 op 重组，通用 payload_dumper 工具会截断。
2. **boot.img**（96MB）：header v4、cmdline 为空（GKI 正常）、kernel 17,341,744 B。
3. **vendor_boot**（128MB）：header v4，`vendor_ramdisk=100,817,771 B`，**结构与旧版一致**：recovery(47,402,581 B) + dlkm(53,415,190 B) 双片段、无 platform 片段，bootconfig 65 B（avb_pk_hash 与 META-INF 断言一致 `40a3ded7…`）。
4. **打包器克隆验证**：`vendor_boot_v4.py clone` 对新固件 vendor_boot 重打 → **与原厂镜像逐字节一致**（布局算法兼容新固件）。
5. **重打包模拟**（repack + `--add-cmdline permissive` + `--retag-recovery`）：
   - 回读 cmdline 确认含 `androidboot.selinux=permissive androidboot.hardware=mt6899 loglevel=8 ignore_loglevel` ✅
   - 两个片段均标记 recovery ✅
   - 产出 101,281,857 B < 分区 134,217,728 B（余量约 31MB）✅
6. **自检脚本**：`check-vendor-fit.sh` 全部通过（KMI 一致、122 条 load 清零缺失、permissive/cmdline/危险开关全 OK）。

## 四、残留注意事项

1. **设备端最终验证**：模拟是静态/重组级验证，首次刷入建议先用 `fastboot boot vendor_boot.img`（若 bootloader 支持临时引导）或备好原厂 vendor_boot.img 以便一键还原。
2. **KMI 补丁级差异已消除**：本次已把内核与模块同步为 6.6.127 同构建，不存在跨版本符号 CRC 风险；`dmesg | grep -E "version magic|disagrees"` 应无输出。
3. **cust/vgc**：仍在 TWRP fstab 中可挂载，但不再列入 fastbootd 动态分区组；刷 oem_zip 仍按 vivo 原厂流程。
4. **AVB**：`vbmeta --flags 0`（关闭校验）策略不变；新 vbmeta 已解出（vbmeta 8KB / vbmeta_system 8KB / vbmeta_vendor 4KB），如需对比可复用本报告提取脚本。
5. OTA zip 内的 `oem_zip/dyn_PD2551_DYNN.zip` 等动态 oem 包未随设备树更新，走原厂 sideload 流程即可。
